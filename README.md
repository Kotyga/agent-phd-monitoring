# agent-phd-monitoring

Агент-консультант для анализа конкурсных списков аспирантуры на основе автоматического парсера.

Проект загружает и нормализует конкурсные списки, рассчитывает текущие статусы абитуриентов по приоритетам, формирует HTML- и Excel-снимки, а затем использует локальную LLM и MCP-инструменты для подготовки персонального отчёта о конкурсной ситуации.

> [!WARNING]
> Проект не является официальным сервисом приёмной комиссии.
>
> В исходных данных, логике расчёта и ответах языковой модели могут содержаться ошибки. Результаты отражают только состояние конкурсных списков на момент последнего обновления и не являются гарантией поступления или официальным решением приёмной комиссии.
>
> Автор не несёт ответственности за решения, принятые на основе результатов работы проекта.

## Возможности

### Парсер конкурсных списков

Проект:

- загружает страницы с конкурсными списками и количеством мест;
- сохраняет исходные HTML-страницы;
- нормализует данные в CSV;
- рассчитывает статусы поступления с учётом приоритетов;
- генерирует HTML-отчёт с поиском по уникальному коду;
- создаёт актуальный Excel-снимок конкурсных списков.

### Агент-консультант

Поверх парсера добавлен агентский слой на базе:

- LangChain;
- MCP;
- локальной LLM через Ollama.

Агент может:

- обновить текущий снимок конкурсных списков;
- получить время последнего обновления;
- найти абитуриента по уникальному коду;
- определить его место, баллы, приоритет и текущий статус;
- проверить попадание в бюджетное окно;
- найти ближайших конкурентов выше и ниже в рейтинге;
- проверить участие соседних абитуриентов в других конкурсных группах;
- оценить текущие шансы на поступление;
- сравнить результат с предыдущим отчётом;
- сохранить новый датированный отчёт в формате Markdown.

## Статусы поступления

В проекте используются следующие статусы:

- `green` — абитуриент проходит на это направление и закреплён за ним;
- `yellow` — абитуриент проходит по конкурсу, но закреплён за направлением с более высоким приоритетом;
- `orange` — абитуриент не проходит на это направление, но проходит на другое;
- `red` — абитуриент не проходит ни на одно направление.

Статусы рассчитываются по текущему снимку данных и могут измениться после обновления конкурсных списков.

## Как работает агент

Типичный сценарий анализа:

1. Агент получает предыдущий сохранённый Markdown-отчёт, если он существует.
2. Запускает обновление конкурсного снимка.
3. Читает время обновления из HTML-отчёта.
4. Получает структуру Excel-файла.
5. Находит абитуриента по:
   - уникальному коду;
   - конкурсной группе;
   - типу места.
6. Определяет ближайших участников выше и ниже в рейтинге.
7. Проверяет другие конкурсные группы этих участников.
8. Анализирует попадание абитуриента в бюджетное окно.
9. Сравнивает результат с предыдущим отчётом.
10. Формирует новый Markdown-отчёт.
11. Сохраняет отчёт в файл с датой и временем в имени.

Пример имени отчёта:

```text
2026_08_03_10_52_16_123456.md
```

Отчёты являются накопительными: каждый запуск создаёт новый Markdown-файл. При этом HTML- и Excel-снимки не являются накопительными и перезаписываются при обновлении.

## Структура проекта

```text
agent-phd-monitoring/
├── agents.py                      # запуск агента
├── mcp_mipt.py                    # MCP-сервер и инструменты
├── src/
│   └── run_pipeline.py            # запуск парсинга и расчётов
├── data/
│   ├── raw/                       # исходные HTML и manifest.json
│   ├── normalized/
│   │   ├── applicants.csv
│   │   └── places.csv
│   └── results/
│       ├── by_direction.csv
│       └── by_code.csv
├── reports/
│   ├── index.html                 # HTML-отчёт
│   ├── admission_snapshot.xlsx    # текущий Excel-снимок
│   └── md/                        # история агентских отчётов
└── logs/
    └── pipeline.log
```

## Основные артефакты

- `data/raw/` — загруженные HTML-страницы и `manifest.json`;
- `data/normalized/applicants.csv` — нормализованные данные абитуриентов;
- `data/normalized/places.csv` — информация о количестве мест;
- `data/results/by_direction.csv` — результаты по конкурсным группам;
- `data/results/by_code.csv` — результаты по уникальным кодам;
- `reports/index.html` — интерактивный HTML-отчёт;
- `reports/admission_snapshot.xlsx` — актуальный Excel-снимок;
- `reports/md/` — датированные отчёты агента;
- `logs/pipeline.log` — лог работы парсера.

## Требования

- Python 3.10 или новее;
- Ollama;
- локальная модель с поддержкой tool calling;
- рекомендуемый размер контекста модели — не менее 16 384 токенов.

Для небольшого контекста длинный системный промпт и описания MCP-инструментов могут полностью занять доступное окно. В таком случае модель может завершить генерацию до первого вызова инструмента.

## Запуск парсера без агента

### Полное обновление данных

```bash
python3 src/run_pipeline.py
```

Команда загружает актуальные страницы, нормализует данные, пересчитывает статусы и формирует отчёты.

### Пересчёт по уже загруженным данным

```bash
python3 src/run_pipeline.py --skip-fetch
```

Параметр `--skip-fetch` пропускает загрузку новых страниц и использует уже сохранённые исходные данные.

## Запуск агента

Убедитесь, что:

1. виртуальное окружение активировано;
2. Ollama запущена;
3. выбранная модель установлена;
4. пути в конфигурации указаны корректно;
5. Excel- и HTML-отчёты существуют либо могут быть созданы парсером.

Запустите:

```bash
python agents.py
```

В начале работы должен появиться список MCP-инструментов:

```text
Доступные инструменты [
  'read_rating_neighbours',
  'get_info_snapshot',
  'read_excel_columns',
  'read_column_value',
  'read_filter_condition',
  'get_current_time',
  'read_dir',
  'write_file',
  'read_file',
  'get_phd_snapshot',
  'read_latest_file'
]
```

После завершения анализа новый отчёт будет сохранён в:

```text
reports/md/
```

## Ограничения

- Проект зависит от структуры страниц приёмной комиссии. При изменении HTML парсер может перестать работать.
- Excel- и HTML-снимки перезаписываются при каждом обновлении.
- История сохраняется только в виде отдельных Markdown-отчётов.
- Языковая модель может неверно интерпретировать данные или не вызвать необходимый инструмент.
- Обязательные операции, например запись итогового отчёта, рекомендуется выполнять программно после ответа агента.
- Попадание в бюджетное окно по позиции не всегда означает фактическое зачисление.
- Необходимо учитывать приоритеты, согласия, оригиналы документов и возможные изменения конкурсных списков.
- Итоговый статус не является официальным решением приёмной комиссии.
